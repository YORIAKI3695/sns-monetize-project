# セキュリティ・個人情報管理設計書(STEP8)

> フォルダ構成(構想書19章)には明示されていないが、STEP8の要求を満たすため `12_Security` を新規提案フォルダとして追加した。
> 本書は一般的な設計上の留意点の整理であり、法的助言ではない。商用化前に弁護士・専門家への確認を推奨する(🔴要確認)。

## 1. 取得する個人情報の分類(🟡仮仕様)

| 情報 | 分類(想定) | 備考 |
|---|---|---|
| 氏名 | 個人情報 | |
| 生年月日 | 個人情報 | 占術計算の根幹データ |
| 出生時間 | 個人情報 | 不明対応あり |
| 出生地 | 個人情報 | 座標変換を伴う場合あり |
| 現在の仕事・悩み | 個人情報(要配慮情報に準じる可能性) | 恋愛・お金等センシティブな内容を含み得るため取り扱いに注意 |
| 過去の転換点・人生で大変だった時期 | 個人情報(要配慮情報に準じる可能性) | 内容次第で機微な情報を含む可能性がある |
| 決済情報 | 決済情報 | 自社で保持しない設計を推奨(下記6章) |

🔴 要検討: 「現在一番気になっていること」等の自由記述欄が、個人情報保護法上の要配慮個人情報に該当する内容(病歴、信条等)を含み得るため、取得目的の明確化と同意取得文言の精査が必要。

## 2. 適用法令の検討ポイント(🔴要確認・専門家相談推奨)

- 国内: 個人情報保護法上の「取得」「利用目的の通知・公表」「第三者提供」の各要件を満たす運用が必要
- 海外(Etsy経由等): 越境移転が発生する場合、GDPR等の域外適用を受ける可能性がある。対象国・対象顧客の有無に応じて要確認
- 本プロジェクトでは断定的な法的結論を出さず、実装・商用化前に専門家確認を行うことを前提とする

## 3. 保存・アクセス制御方針(🟡仮仕様)

- `customers` テーブルの氏名・生年月日・出生時間・出生地は保存時暗号化(at-rest encryption)を推奨
- アクセス権限は最小権限の原則(鑑定業務に必要なロールのみアクセス可能)とする
- 🔴 要検討: 具体的な暗号化方式・鍵管理方針、利用するクラウド基盤([[08_Automation/自動化フロー設計書]] のDB選定と連動)によって実装方法が変わる

## 4. 同意取得(🔴要検討・未整備)

- プライバシーポリシーの整備、鑑定目的外利用(メソッド検証への二次利用等)についての同意取得文言が未作成
- [[10_Test_Data/テストデータ_サンプル顧客テンプレート]] で触れた「実データをメソッド検証に使う場合の同意」もここで方針を定める
- 同意記録は `consent_logs` テーブル案([[05_Database/データベース設計書]] 参照)で管理する想定

## 5. データ保持期間・削除ポリシー(🔴要検討・未定)

- `life_waves` `annual_readings` は「10年、20年と参照できる設計」がサービスの核であるため、原則長期保存が前提
- 一方で個人情報保護の観点から、退会・削除請求への対応フロー(顧客からの削除依頼にどう応じるか、鑑定履歴が失われることの説明含む)は未設計
- 🔴 要検討: 削除請求と「人生波動カルテとしての継続性」という商品価値がトレードオフになるため、方針決定が必要

## 6. 決済情報の取り扱い(🟢確定仕様・方針のみ)

- 自社データベースにカード番号等の決済情報を直接保持しない設計とする(決済代行サービス利用を前提とする)
- 具体的な決済代行の選定は [[08_Automation/自動化フロー設計書]] 参照(未選定)

## 7. アクセスログ・監査(🔴要検討・未着手)

- 顧客の個人情報・鑑定データへのアクセスログ取得方針は未設計
- 自動化が進みAIが鑑定文を生成する場合、外部AI APIへの個人情報送信範囲(氏名等を含めるか、匿名化した属性のみ送るか)の設計が必要(🔴要検討・重要)

## 8. インシデント対応(🔴要検討・概要のみ)

- 情報漏洩等が発生した場合の報告フロー・顧客通知フローは未整備。事業規模の拡大に応じて別途整備する

## 9. 本書のサマリー(現状のステータス)

現段階では方針の骨子のみであり、確定仕様と言えるのは「決済情報を自社保持しない」という方針程度にとどまる。個人情報保護法・海外法令への具体的な対応、同意文言、削除ポリシーは全て実装着手前に確定させるべき**要検討事項**として扱う。
