# 鑑定ロジック設計書(STEP5)

> [[02_Method/波動鑑定メソッド仕様書_v0.1|波動鑑定メソッド仕様書]](SSOT)で定義された未確定パラメータを、実装可能な粒度に分解した設計書。
> 本書のパラメータが確定した際は、必ずSSOT側にも反映すること。

## 1. 全体処理フロー(🟢確定仕様・順序)

```
1. 顧客の出生情報(生年月日/出生時間/出生地)を取得
2. 各占術の計算エンジンで生データを算出
   - 四柱推命 → 大運データ
   - 西洋占星術 → トランジットデータ
   - 数秘術 → 個人年データ
3. 生データを波動スコア(-100〜+100)に変換 【🔴要設計】
4. 占術ごとの重み付けを適用して合成スコアを算出 【🟡仮仕様】
5. 人生3大波動を算出(初回のみ。以降は再利用) 【🔴要設計】
6. 現在波動(年間)を算出(毎年) 【🔴要設計】
7. 人生3大波と現在波を突き合わせ、一致判定を実施 【🔴要設計】
8. 一致判定結果と各スコアから5段階の波動レベルを算出 【🔴要設計】
9. 判定結果をもとに鑑定文(AI生成)・チャートを生成
```

## 2. 波動スコア変換(🔴要設計・最重要の未確定項目)

現状、SSOTには「-100〜+100の目盛り」しか定義がなく、**占術の生データをその目盛りに落とし込む写像関数が存在しない**。設計にあたり検討すべき論点を以下に整理する(結論は未確定)。

- 四柱推命の大運: 大運の十干十二支と日主(生まれた日の干)との五行関係(比肩・食神・偏財・七殺 等の十神)を強弱に変換する案が考えられるが、具体的な対応表は未作成
- 西洋占星術のトランジット: ハードアスペクト(スクエア・オポジション)を下降方向、ソフトアスペクト(トライン・セクスタイル)を上昇方向とする案が考えられるが、対象天体・対象アスペクトの範囲・orb(許容誤差角度)が未定義
- 数秘術の個人年: 1〜9の個人年ナンバーそれぞれに固有の「上昇/停滞/転換」の意味を割り当てる案が考えられるが、対応表は未作成

🔴 **要検討タスク**: 上記3つの変換表(マッピングテーブル)を、鑑定士としての専門知見または占術文献を根拠に確定させる必要がある。これは技術設計ではなく**占術知識に基づくコンテンツ設計**であり、プロジェクトオーナー(鑑定士本人)の判断が必須。

## 3. 重み付けの実装方針(🟢確定仕様・仕組み/🟡仮仕様・数値)

- 重み付け数値(四柱推命50%・西洋占星術30%・数秘術20%)はDBまたは設定ファイルに保持し、**コード変更なしで変更可能**にする(下記 `wave_score_config` テーブル案、[[05_Database/データベース設計書]] 参照)
- 検証方法(🔴要検討): 実際の顧客の「過去の人生の転換点」入力データ(STEP9の入力項目)と、算出された波動スコアの転換点を突き合わせ、一致率を検証する運用を想定。具体的な検証手順・サンプルサイズ・合否基準は未定

## 4. 人生3大波動の算出(🔴要設計)

- 四柱推命の大運は通常、生涯にわたり複数(8〜10個程度)存在する
- そこから「3つ」に絞り込む基準が未定義。想定される論点:
  - 波動スコアが特に高い/低い上位3つを機械的に抽出する案
  - 人生を三分割(青年期・壮年期・老年期 等)し、各期の代表的な大運を1つずつ選ぶ案
- 🔴 **要検討**: どちらの方式を採用するか、またはそれ以外の方式か

## 5. 現在波動の算出(🔴要設計)

- 対象年度の1年間(または鑑定実施日時点)のトランジットをどの粒度で集約するか未定(年間平均、年始時点のスナップショット、複数回のピーク検出 等)
- 数秘術の個人年を「年間テーマ」としてどう文章に反映するかは [[07_Certificate/PDF鑑定書仕様書]] 側の表現設計と連動

## 6. 一致判定ロジック(🔴要設計・仮の考え方のみ)

SSOTで定義された仮案(上昇+上昇=シンクロポイント、上昇+下降=準備調整ポイント)を数式に落とすたたき台:

```
差分 = 現在波動スコア - 人生波動スコア(該当波)
※ 具体的な閾値・場合分けは未確定
```

🔴 要検討: 差分がどの範囲でどの判定区分になるか。また両方が下降/両方が安定の場合の判定区分名称・意味づけも未定義(SSOT第4章と同じ課題)。

## 7. 5段階レベルへの集約(🔴要設計)

- 人生3大波(3値)、現在波(1値)、一致判定結果という複数の入力から、最終的に1つの5段階レベルを出す合成ロジックが必要
- 想定される方式(いずれも未決定):
  - 加重平均スコアをそのまま5段階の閾値と比較する方式
  - 一致判定の区分ごとに固定レベルを割り当てるルールベース方式
- 🔴 要検討: 上記いずれか、またはハイブリッド方式か

## 8. パラメータ外部化の設計方針(🟢確定仕様)

以下は全てコードに埋め込まず、設定テーブル(`wave_score_config` 等)またはコンフィグファイルとして管理し、**プロジェクトオーナーが実データ検証をもとに調整できる**構造とする。

- 占術ごとの重み付け比率
- スコア変換マッピングテーブル
- 一致判定の閾値
- 5段階レベルの判定閾値

設定変更時は `calculation_version` をインクリメントし、過去の鑑定結果に影響を与えないようにする([[05_Database/データベース設計書]] 参照)。

## 9. 検証・テスト方針(🔴要検討)

- 実データ(顧客の過去の転換点入力)を用いた検証プロセスの設計は未着手
- 手動鑑定(鑑定士本人によるレビュー)とロジック算出結果を突き合わせるテスト運用が必要と想定されるが、具体的な手順は [[00_Project/02_実装ロードマップ]] のPhase1で検討する
